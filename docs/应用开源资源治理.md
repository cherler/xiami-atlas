# 场景页应用开源资源治理

## 结论

场景页不是开源项目排行榜，也不是「推荐什么」的结论页。它是一个**按真实应用组织的公开资源索引**：用户先选要交付的东西，再看到能继续查证、学习或运行的项目、Skill、文档和课程。

资源是否进入页面，靠可追溯来源、应用关联、公开可访问、许可证信息和持续可维护性；不靠一句「我们认为它最好」。

当前页面继续保留四个菜单，不新增「开源」菜单。应用页内部的资源按以下顺序组织：**可直接运行的项目 → Skill / Workflow → 文档 → 课程**。这是使用路径排序，不是质量评分。

## 一、来源与证据

资源的 `src` 是证据来源；资源的 URL 是用户实际访问的规范入口。两者不能只填一个：

| 来源层 | 可以做什么 | 不能单独做什么 |
|---|---|---|
| S：官方仓库、官方模型卡、官方文档、官方课程、官方发布页 | 证明项目归属、版本、安装方式、文档内容、许可证声明 | 不能证明实际效果一定达到宣传水平 |
| A：独立数据、论文、基准测试 | 补充采用度、研究背景、独立测量 | 不能替代项目本身的许可证和运行说明 |
| B：高质量二手资料 | 发现候选资源、寻找原始入口 | 不能作为收录后的唯一证据 |
| C：社区帖子、视频、博客、Fork | 发现工作流、技巧和替代实现 | 不能单独证明官方状态、许可证或长期可维护性 |

来源分级沿用 `data/sources.json` 的 S/A/B/C；`atlas.json` 里的来源条目负责页面引用，`data/sources.json` 负责可自动检查的更新周期。两套登记中的同一个资源，最终应使用稳定一致的来源 ID，避免「页面引用更新了、监视器却没盯」的断裂。

每条已发布资源至少要能回溯到：

- 规范 URL、来源 ID、资源类型，以及它关联的应用 / Skill；
- 原文摘录或明确的证据说明；
- 许可证名称或「未声明」；
- 最近一次人工核验时间；
- 最近一次机器检查时间，以及上游最后更新时间（如果上游提供）。

许可证未声明不等于没有许可证。它可以作为候选进入审核队列，但不能在页面上被写成「开源」或「可商用」。

## 二、入选条件

### 硬门槛

以下条件全部满足，才可以从候选变成页面上的「已发布」资源：

1. **直接服务于应用。** 能对应至少一个关联 Skill，或者是这个应用必需的基础课程 / 官方文档；不能只是换了一个名字的能力介绍。
2. **公开可访问。** 不要求购买、订阅或登录才能拿到核心内容；付费平台的落地页不作为资源收录。
3. **有可验证内容。** 项目要有 README / 模型卡 / 示例 / 安装说明中的至少一项；Workflow / Skill 要能看到依赖和使用入口；课程 / 文档要能打开到实际内容。
4. **有稳定入口。** 优先收录上游仓库、模型卡和官方文档，不收录只存在于转载页、短链或个人网盘的副本。
5. **许可证口径清楚。** 已知许可证正常收录；自定义社区许可要按原名标注；未声明许可证只能标为待核，不标「开源」。
6. **不是重复镜像。** 上游仓库优先于 Fork；只有在 Fork 有明确独立维护、额外节点或关键修复时，才作为变体收录。
7. **没有明显失效信号。** 已删除、长期不可访问、官方标记 archived，或内容明显与当前项目无关的资源不发布。

### 软信号

Star、下载量、Fork 数、最近提交、Issue 响应和版本发布可以帮助排序和发现，但任何一个都不能单独构成入选理由。尤其不能把 Star 数直接翻译成「更可靠」或「更适合」。

## 三、更新与迭代频率

把「机器看到了变化」和「我们重新核过内容」分开记录：`last_seen_at` 只是监视器看到上游动过，`checked_at` 才表示页面引用和资源状态重新核过。

| 资源类型 | 机器检查 | 人工 / Agent 复核 | 触发即时复核的事件 |
|---|---:|---:|---|
| GitHub 项目、模型仓库、Workflow、Skill | 7 天 | 30 天 | 新版本、许可证变化、archived、安装方式变化 |
| 官方文档、官方发布页 | 7–14 天 | 30 天 | 页面结构变化、版本号变化、关键教程被移除 |
| 社区项目或社区 Workflow | 7–14 天 | 30 天 | 新 release、依赖大改、连续构建失败 |
| 公开课程 | 90 天 | 180 天 | 课程下线、章节重写、链接转收费或需要登录 |
| 基础参考文档 | 30 天 | 180 天 | 目标版本停止维护、内容迁移或链接失效 |

默认只对 `data/sources.json` 中登记且到期的来源运行 `scripts/watch.mjs --due`。程序负责抓取、快照、指纹和 Diff；它不直接把变化写成前台事实。变化进入候选队列后，再由人工 / Agent 判断：

```text
来源登记 → 到期检查 → 快照 / Diff → 候选变化 → 复核证据 → 更新资源 → 场景页聚合
```

以下情况要保留原资源 ID 并更新元数据，而不是删除后重建：仓库改名、URL 迁移、项目发布新版本、文档路径变化。只有上游确实消失、重复或不再服务该应用时，才进入归档。

## 四、状态、过滤和淘汰

资源内部使用四种状态：

| 状态 | 含义 | 默认是否展示 |
|---|---|---|
| `candidate` | 发现了，但许可证、关联或可复现性还没核完 | 否 |
| `published` | 硬门槛通过，允许进入场景页 | 是 |
| `stale` | 超过复核周期，或上游长期没有可确认的更新 | 是，但标「待复核」；用户可隐藏 |
| `archived` | 删除、停更、重复、转收费或与应用脱钩 | 否；在历史记录中保留原因 |

页面默认过滤：

- 隐藏 `candidate` 和 `archived`；
- `stale` 不从数据库删除，但默认排在有效资源之后，并提供「隐藏待复核」开关；
- 去掉无应用 / 无 Skill 关联、无规范 URL、需要付费才能使用核心内容、只有宣传没有可验证材料的条目；
- 同一规范 URL只保留一张卡；同一项目的多个应用关联使用同一个资源记录，不复制改写；
- 许可证未知时，允许进入候选和审核页，不进入「开源已核」默认结果。

推荐的用户过滤项只有事实过滤，不做「推荐指数」：`全部`、`项目`、`Skill`、`文档`、`课程`、`官方来源`、`许可证已声明`、`最近 90 天检查`、`隐藏待复核`。

## 五、排序方法

排序采用稳定的多级规则，不把不同性质的信号压成一个看似精确的可信度分数：

1. 只展示 `published`；若用户打开待复核，则 `published` 在 `stale` 前。
2. 按可执行程度排序：`project` → `skill` → `docs` → `course`。
3. 同类型内，官方来源优先于第三方来源；社区资源不因为热度高而越过官方规范入口。
4. 直接关联当前应用 Skill 的资源优先于泛用参考资料。
5. 同等条件下，最近核验 / 最近上游更新的资源优先；超过 180 天未核验的资源进入待复核层。
6. 最后才用下载量、Star、Fork 等采用度信号打破平局，并且不在页面上把它写成质量保证。
7. 所有仍相同的条目按资源名称和规范 URL稳定排序，保证页面不会因为抓取顺序变化而跳动。

前台展示来源、资源类型、关联 Skill 和核验日期；不展示「可信度 87 分」「推荐指数」或「最适合某类人」这种结论。排序可以帮助用户先看到什么，但不替用户判断项目在当前版本下是否一定有效。

## 六、数据结构迭代

当前 `ApplicationResource` 已有 `kind / name / url / src / quote / note / skill_id`，足以支撑第一版公开路线，但还不能完整表达更新状态。下一次数据结构迭代应补充以下可选字段，逐步把人工维护变成可检查的资源目录：

```ts
{
  resource_id: string,          // 稳定主键，不随名称或 URL 迁移改变
  status: "candidate" | "published" | "stale" | "archived",
  watch_src?: string,           // data/sources.json 中的监视来源
  license_status?: "declared" | "custom" | "unknown" | "not_applicable",
  license_name?: string,
  checked_at?: string,          // 人工 / Agent 复核
  last_seen_at?: string,        // 机器最近看见上游
  upstream_updated_at?: string, // 上游提供的最后更新时间
  archived_reason?: string
}
```

在这些字段补齐前，场景页只显示已经存在的来源和原文，不伪造「最近更新」「许可证已核」标签。第一批应优先给当前六个应用使用的官方课程、ComfyUI 文档和官方项目补齐监视来源，再扩展到 Skill 自动汇总的社区仓库。

## 七、验收标准

- 每个已发布资源都能从页面卡片回到规范 URL和来源原文；
- 页面不会出现付费平台导流链接；
- 资源更新不会自动生成新的结论式评语；
- 上游变更只生成待处理 Diff，不自动覆盖人工核过的描述；
- 资源失效、许可证变化、转收费和 archived 都有状态变化和原因；
- 同一个资源被多个应用使用时只维护一份基础记录；
- 刷新页面或新增来源后，已发布资源的顺序仍然稳定；
- 排序依据可以在方法页解释，但不对外包装成质量或效果保证。

## 八、应用命名的证据上限（2026-08-10 采集结论）

问过一轮「这几个应用名，行业里到底叫不叫这个」。结论是：**厂商不发布应用分类法，B 级就是这件事的证据上限**，不必再去找 S 级。

抓取实况：

| 目标 | 结果 |
|---|---|
| 海螺 hailuoai.video | 拿到官方分类，但都是**玩法/模板名**：Trending、Ads、LoveFrame、PetPal、BabyForm、PlayFun、SnapMorph、Style Switch、CineScope、ASMR |
| 可灵 klingai.com/app | 登录墙 + SPA，只拿到导航壳：创意圈 / 资产 / Omni / 生成 / 灵动画布 / 全部工具 |
| 即梦 jimeng.jianying.com | 同上，只拿到：灵感 / 生成 / 资产 / Agent 模式 / 短片 / 活动 |
| 阿里云 · 短剧漫剧场景 | 三条场景：AI换装-短剧、智能视频拼接、小说故事与角色批量生成 |
| 火山引擎 | 云侧方案名：多模态视频理解与生成方案、电商多模态素材生成方案 |

三种组织方式，没有一种按交付物：消费端 App 按**玩法**分，云厂商按**能力方案**分，阿里云那页最接近应用层但只有三条且颗粒度混着（AI换装是玩法，小说批量生成是工序）。

「AI短剧 / AI漫剧 / 小说推文 / 数字人口播」这类**交付物**分类，是行业媒体与创作者社群在用，厂商不用。所以：

- `applications[].zh` 与 `aliases` 的证据层级是 **B**（行业媒体 + 工具导航站 + 艾媒《2025-2026 中国AI漫剧行业趋势白皮书》），**不标注为厂商官方**；
- 不要再为这一层去找厂商官方来源 —— 上面已经证明它不存在；
- 真要升级证据，只能靠**平台侧的用词统计**（如各站分类词频）或**行业报告的正式定义**，而不是厂商产品页。

顺带一条对照：海螺的玩法分类里有 ASMR、宠物、婴儿、情侣这类，我们的应用层一条都没有 —— 那是**玩法**不是交付物，按本文档第二节「不能只是换了一个名字的能力介绍」的同一条理由，不收。
