# 更新一个模型版本 · 完整清单

> **为什么有这份清单**:2026-08-29 升 Gemini 3.7 / GLM-5.3 / Grok 4.6 时,只改了模型的当前版本字段和能力格,**漏了 `versions[]` 里的发布记录**——结果「演进树/谱系」还停在旧版,用户一眼看出来了。
>
> **为什么不做成自动校验**:试过。`model.version`(如 `Gemini 3.7 Flash`)和 `versions[].version`(如 `Gemini 3.7`)全站命名口径不一致(大小写、带不带 tier、日期码……),自动匹配会**冤枉 13 个本来没问题的模型**,违反「新检查不能冤枉好数据」。所以这一步只能靠清单守,不能靠校验守。**升版时人肉过一遍这张单子。**

---

## 升一个模型版本,要改的地方(缺一不可)

### 1. `data/atlas.json` › `models[]` 里那个模型
- [ ] `version` → 新版本
- [ ] `version_as_of` → 核验日(不是发布日)
- [ ] `version_src` + `version_quote` → **核心模型必需**(R66),要有可引官方原文
- [ ] 若引了新发布页 → `sources[]` 加一条 `{url, name, tier:"official"}`

### 2. `data/atlas.json` › `support[]` 能力格(R9)
- [ ] 该模型 `verified_for === 旧版本` 且**没有 sibling** 的格 → 加 `recheck: "新版本"` + `note`(旧结论核在旧版,新版待重核)
- [ ] `sibling` 的格(同门别支,如 glm 的 glm-4-air/voice)**不要动**
- ⚠️ 扩展层模型**也可能有能力格**(如 grok),照样要 recheck——别以为 extended 就免

### 3. `data/atlas.json` › `versions[]` 加一条发布记录 ★最容易漏★
> **演进树 / 谱系(components/Tree.tsx, Genealogy.tsx)是从这个数组建的,不是从 `models[].version`。**
- [ ] 加 `{ id, m, version, date, added, src, quote, parent, cap 或 cap_skip }`
  - `id`:`<m>-<version>-<短描述>`
  - `m`:模型 id
  - `version`:代号(如 `Gemini 3.7`,可与 model.version 的全名不同)
  - `date`:**发布日**
  - `added`:这代新增了什么
  - `parent`:**上一版发布记录的 id**(连演进树的边,要真实存在)
  - `cap`:新增能力轴 id;若没采到 → 用 `cap_skip` 写原因

### 4. `data/changes.json` 加一条事件
- [ ] `{ id, date, side:"world", kind:"版本更迭"或"新模型", subject, before, after, why, impact:[m], src, models:[m], domain }`

### 5. 不要碰的
- [ ] **别改 `generated_at`**:它是星数据(stars_per_month)的基准日,一改就触发 R88 星速对不上。模型版本各自带 `version_as_of` 就够了。

### 6. 收口
- [ ] `node scripts/validate.mjs` → **EXIT 0**(重点看 R66 有源、R9 recheck、R88 星速)
- [ ] 上线走三道闸:见 `deploy/README.md`(DONE_0 / 日志有内容 / 本机页数==服务器页数)

## 口径备忘
- **闭源旗舰追哪一档**:Gemini 追 Flash(workhorse),Claude 目前追 Fable 5(frontier)不追 Opus 5(更便宜的默认款)——口径不一致时在条目 note 里写明,别默认翻。
- **开源旗舰 vs API-only**:旗舰若只有 API、HF 上只有变体,先不升(记 note);等完整权重上 HF 再升(GLM 5.3 就是这么等到 08-25 才升的)。
