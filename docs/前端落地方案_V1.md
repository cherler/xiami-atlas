## 二、五条验收约束

每做完一页，逐条过一遍。不过就重做，不解释。

1. **删掉正文测试（§7.1）** —— 把这一页所有句子删掉，只留标题、节点、线、数字、图标、日期。还能看懂在说什么吗？看不懂，说明信息在文字里而不在结构里。
2. **一页一问（§4）** —— 这一页回答的问题，能不能用一句话写在 `<h1>` 里？写不出来，这页不该存在。
3. **不解释自己（§52.5）** —— 页面正文里不许出现「我们如何……」「之所以……是因为我们……」。这类话一律去 `/method`，原地只留角标。
4. **克制（§52.1）** —— 前台永远只放最重要的。全量数据放二级页，并明确标「代表性视图，不是完整列表」。
5. **可追溯（§52.4）** —— 每条重要事实旁边必须能点到来源、核验日期、录入身份。但它是**角标，不是段落**。

## 七、存储：为什么留 JSON，什么时候该换（2026-08-08 决定）

项目负责人问：为什么不用 SQLite / DuckDB？

**先量，再答。**

```
.git 24M，其中：
 11.6 MB  assets/atlas-demo.mp4        ← 演示视频
  4.4 MB  assets/matrix-*.png
  3.2 MB  assets/atlas-demo-v.mp4
  1.9 MB  assets/demo-raw-v/v.webm
  1.1 MB  data/atlas.json（全部历史加起来）
  0.6 MB  data/snapshots/（53 个文件，当前）
```

**JSON 不是瓶颈，提交进 git 的媒体文件才是**（21MB / 24MB）。

### 为什么 curated 数据继续用 JSON

因为**审核机制就是 git diff**（§59.4.c）：commit = Revision，diff = ChangeEvent，
commit 作者区分人和 bot。三色通道（§59.3）的绿色通道自动写入之后，
人要做的事就是**看那次 diff**；出错了就 `revert`。

换成 SQLite，git 只看得见「一个二进制块变了」——
**这套审核和回滚机制会当场消失，然后我们得重新造一个审核后台。**
§42 明确说过现在不上 CMS。

这是少数几个「一个能 diff 的文件」严格胜过数据库的场景。

### DuckDB：当查询层，不当存储层

DuckDB 直接读 JSON，零迁移：

```sql
SELECT v.m, count(*), min(v.date), max(v.date)
FROM (SELECT unnest(versions) AS v FROM read_json_auto('data/atlas.json'))
GROUP BY v.m ORDER BY 2 DESC;
```

「哪些模型在某个季度加了能力」这类问题，SQL 三行、手写 JS 二十行。
**要 SQL 的好处，不必付换存储的代价。** 见 `scripts/q.sh`。

### 同步与上线

站是**静态导出**，数据在构建时编进页面 —— **服务器上不需要数据库**，
